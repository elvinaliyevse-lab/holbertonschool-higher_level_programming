I just finished a project on how Python handles objects, and the thing that made it click was a bug I'd been ignoring.

I had a function that was supposed to return "BestSchool" one more time on every call. It returned an empty string instead. Every time. No error, no crash — it just quietly did nothing, and I hadn't noticed.

It all comes back to one idea: in Python, everything is an object, and a variable is just a name pointing at one.

Two names can point at the same object:

a_list = [1, 2, 3]
b_list = a_list
b_list.append(4)
print(a_list)      ->  [1, 2, 3, 4]

No copy happened there. Lists are mutable, so a change made through one name shows up through the other.

Strings can't do that. They're immutable, so this quietly builds a brand new object:

t = "Best"
t += "School"      ->  id(t) is now different

That same difference explains why passing something into a function sometimes changes the caller's data and sometimes doesn't. It isn't about functions at all — it's about whether the object can be modified:

def add_item(items): items.append("new")     -> caller sees the change
def rebind(items):   items = ["different"]   -> caller sees nothing

Same syntax. Opposite results.

And the empty-string bug? The fix turned out to be a mutable default argument, normally considered one of Python's classic traps:

def magic_string(count=[0]):
    count[0] += 1
    return ", ".join(["BestSchool"] * count[0])

Default arguments are evaluated once, when the function is defined, and then stored on the function object itself. Because that default is a list, it's mutable, so it survives between calls and carries the count. The exact behaviour behind the famous bucket=[] bug is the thing that makes this work.

One more that caught me out: most tutorials say that 257 is 257 evaluates to False in Python. On 3.12 it gave me True, because the compiler stores that constant once per block of code. You have to write int("257") is int("257") to actually see False.
